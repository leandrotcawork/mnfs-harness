# Harness 0.5 — Design de Execução no Claude Code

Data: 2026-07-29 · Status: aprovado por seções pelo operador (6/6) · Complementa: `docs/STUDY-HARNESS-0.5-ROUTER.md` (v2 FUSÃO Claude×Sol)

Este documento fixa COMO o desenho 0.5 vira sistema concreto no Claude Code Desktop. O STUDY define a doutrina (peças A-E, refutações, fases); este spec define a montagem: primitivas, arquivos, protocolos e processo de construção.

---

## 0. Decisões travadas na entrevista (2026-07-29)

| Pergunta | Decisão |
|---|---|
| Escala | 1 operador, 1 máquina; Claude Code Desktop com MCP de mensagens entre sessões (mantido — não construir transporte próprio) |
| Piloto | o próprio repo mnfs-harness (dogfood desde o 1º commit) |
| Runtime | Node.js único; hooks bash = cascas finas de ~3 linhas chamando `node runtime/*.mjs` |
| mnfs-workflow | absorvido no roteador 0.5 — plugin único `mnfs-harness` |
| Budget | só tokens/tempo (sem dinheiro por ora) |
| Critério de sucesso primário | QUALIDADE do código mergeado: sem slop/fallback/mock escondido, seguindo regras do repo; missão sai operando ponta a ponta. Custo/velocidade secundários. QA/review continua existindo como validador |

**Abordagem escolhida: A — plugin-nativo, git como banco.** Zero daemon, zero DB, zero serviço. Abordagem B (conductor como runtime via Agent SDK) descartada: abandonaria Desktop+MCP. Conductor sobrevive como VIEWER read-only futuro (consome `state-view.schema.json`), nunca dono do estado.

<repo-produto>/.mnfs/

## 2. Seção 1 — Roteador `/harness`

- `routing.json` é a única fonte da matriz de dispatch (hoje duplicada em 5 lugares). Entrada: `intent → {card, lane, gates[], seats[], risco-base}`. Hooks e skills LEEM; ninguém copia tabela.
- Intents iniciais: `mission`, `milestone`, `feature`, `dispatch`, `review`, `integrate`, `replan`, `status`, `plan` (dry-run). Absorvem os comandos do mnfs-workflow.
- Cartões ≤60 linhas: O QUE fazer, apontando schema e template. Doutrina vira gate ou morre.
- HARNESS-CORE encolhe para ~150 linhas de lei (invariantes). O resto: vira enforcement, vira cartão, ou é deletado.
- **Lane barata obrigatória**: intent pequeno (1-2 arquivos, risco baixo pelo resolver) = sessão única, sem hub, sem chips, sem dual-gate. Decisão pela classe de risco, não pelo hábito.
- `/harness status` lê state.json → "M01-F02 IMPLEMENTING ∥ M01-F03 IN-REVIEW".
- dispatch-lint 2.0: valida prompt de dispatch contra routing.json + manifest hashado (não regex em prosa).

## 3. Seção 2 — Máquina de estado + eventos

- `.mnfs/events.jsonl`: um evento por linha com `seq, ts, type, mission/milestone/feature, actor, payload, prev_hash, hash`. Cadeia de hash detecta truncamento/edição.
- `state.json` = projeção via `runtime/project.mjs`. `replay --at-event N` reconstrói e compara hash — divergência = corrupção detectada.
- FSM por feature: `PLANNED → DISPATCHED → BOOT-ACK → IMPLEMENTING → IN-REVIEW → INTEGRATING → CLOSED`, desvios `BLOCKED`/`REPLAN`. Transição ilegal = projetor rejeita (fail-closed). Milestone/missão = agregação.
- Só o runtime grava evento (`runtime/emit.mjs`). Worker emite CLAIM por mensagem; hub valida e emite evento.
- Hooks leem estado, nunca transcript (mata classe D-7). Projeção incremental via cursor embutido no state.json — hook projeta só delta.
- `state-view.schema.json` desde F0: contrato read-only para `/harness status` hoje, deck amanhã.

### Telemetria — fontes concretas
1. **Tokens/custo**: parser do transcript JSONL da sessão (`~/.claude/projects/<proj>/<session>.jsonl`, campo `usage` por mensagem); trecho BOOT-ACK→CLAIM; custo = tokens × `schemas/pricing.json`.
2. **Latência**: derivada dos `ts` dos próprios eventos (dispatch→ACK, ACK→CLAIM, CLAIM→verdict).
3. **Retries**: campo `attempt` nos eventos.
4. **Gates**: `GATE_RESULT {gate, verdict, deciding_criteria[], duration}` como evento normal.
- Degradação: parser quebrou → `tokens: null, reason: "parse-failed@vN"` — nunca trava trabalho. EXCEÇÃO: budget guard exige consumo confirmado; unknown = estimativa conservadora (fail-closed no orçamento, fail-open na medição).
- OTEL descartado (exigiria collector = daemon); anotado como upgrade se um dia multi-máquina.

## 4. Seção 3 — Cadeia de confiança + gates compilados

- Worker emite **CLAIM** ("critérios X,Y,Z, tree-hash T, comandos C"), nunca veredicto.
- **RECEIPT** só de runner harness-owned: `runtime/receipt.mjs` roda comandos FRIO em worktree limpo no tree-hash T; worker não escreve em `.mnfs/receipts/` (settings deny + merge-gate valida origem).
- Tree-hash binding: commit novo → recibo morto.
- **Clausura fria no merge**: validation-contract declara DAG de critérios; merge-gate reexecuta a clausura transitiva dos `deciding` fria (nem tudo, nem amostra: a clausura).
- **Tipos de critério**: `static` (lint/tsc/knip) · `executable` (testes/build frios) · `live` (agent_browser dirige UI real ANTES de paper review) · `judgment` (revisor, só onde julgamento importa). **Contrato micro de cada tipo = entregável do design de F3, não deste documento** (compromisso explícito com o operador).
- **Assentos por risco**: BAIXO = static+executable, zero revisor · MÉDIO = +1 revisor · ALTO = dual-gate + plan-gate. Risk resolver fail-closed: paths × reachability reversa × efeitos declarados como lower-bound; análise incompleta = risco máximo.
- Finding só vira finding após tentativa de confirmação (anti-FP).
- **Oráculo de composição**: 1º contato A→B gera critério com fixture independente do produtor; aresta produtor→consumidor PERSISTE; mudança de contrato/output/alcance em qualquer lado torna o critério deciding de novo.

## 5. Seção 4 — Context-pack (duas camadas)

**Camada 1 — feature.md (missão escreve; intenção, não apodrece).** Seções obrigatórias (schema valida, dispatch bloqueia se faltar): critérios EARS · invariantes · negativos · referência de contrato (aponta, não cola) · spec da fixture do oráculo · fronteiras/dependências.

**Camada 2 — context-pack (gerado no dispatch por `runtime/pack.mjs`; chão, sempre fresco).** Passos: lê feature.md → resolve contrato (cola trecho literal + `path@sha` ATUAL) → zona de código via dependency-cruiser/`go list -json` (lista fechada: toca / só lê) → convenções extraídas com exemplos file:line (anti-Flappy-Bird) → Exemplo-IO executável → fixture do oráculo concreta (worker vê ANTES o teste que o julgará) → sela `pack_hash` + commit-base + ts.

Proteções: **TTL/freshness** (base avançou além do limite → dispatch bloqueado até recompute) · **knip/deadcode no static gate** (slop mecânico) · **`/harness plan` dry-run** (roda pack.mjs para todas as features SEM abrir sessão; pega contrato inexistente, zona vazia, colisão de zonas, dependência circular — no planejamento).

Tooling: regra de admissão = output **determinístico e hashável** (mesmo repo+sha → mesmo pack). dependency-cruiser, knip, go list, deadcode, git show: entram. RAGflow: rejeitado (semântico/aproximado/serviço). Graphify: só se piloto F2 mostrar buraco. Serena MCP (LSP): ferramenta opcional do WORKER, harness não depende.

## 6. Seção 5 — Sessões, mensagens, integração

**Modelo de sessões: sessão = executor descartável · arquivo = memória · FSM = hierarquia.**
- HUB por missão (única sessão longa; descartável também — rotação por milestone permitida como higiene: estado reconstrói do log).
- WORKER por feature: nasce com pack, implementa, emite CLAIM, morre.
- **SEM sessão de milestone** (decisão provada): trabalho dela redistribuído — acompanhamento → FSM/status (grátis) · validação → agente frio `milestone-reviewer` de gate · triagem → nível A: falha comum virou mecânica (receipt diz qual critério falhou; hub lê 1 linha, re-despacha attempt 2) · nível B: 2ª falha idêntica → agente `triage` descartável por incidente investiga FORA do hub e devolve ponteiro para diagnóstico. Hub NUNCA debuga; lê ponteiros e decide.

**Protocolo de mensagem = ponteiro, nunca payload** (≤1 KB, hook rejeita mensagem gorda; conteúdo em arquivo hashado):
`DISPATCH → BOOT-ACK ← CLAIM ← VERDICT → REBASE-REQUIRED →`. BOOT-ACK obrigatório com manifest_hash: hash errado ou silêncio além do timeout (parâmetro `boot_ack_timeout` em routing.json; valor inicial definido no design de F1) = dispatch falho, nada avança. Toda mensagem espelha evento — mensagem perdida ≠ estado perdido.

**Integração (CAS/fencing git-nativo):** lease por evento (`LEASE_GRANTED {token, generation, base_sha}`); merge = `git update-ref <ref> <novo> <esperado>` — atômico, corrida perde no git, não em JSON; perdedor recebe REBASE-REQUIRED → pack recompute no estado integrado → composição reexecuta → retry com generation+1. Token+generation revalidados NO INSTANTE do merge.

**Anti-doom-loop:** 2ª falha idêntica (assinatura de classe no REJECT) = hook bloqueia 3º dispatch, força `/harness replan` (problema é spec, não execução). Replan falhou → agente frio de outro vendor (Codex via runtime existente). Causa raiz persiste em `defect-classes.json` → negativo nos packs futuros.

## 7. Seção 6 — Fases, camada GPT, migração, non-goals

| Fase | Entrega | Prova |
|---|---|---|
| **F0 Fundação** | events.jsonl+projetor+FSM+schemas (event/manifest/claim/receipt/state-view/telemetry)+emit/project/replay+KATs+drill de falha+release atômico do plugin | esqueleto andante: evento real gravado→projetado→replayado, hook lendo state.json no mnfs-harness |
| **F1 Roteador** | routing.json+/harness+cartões+lane barata+dry-run plan+budget (reserva/débito)+CORE→150 ln | intent pequeno ponta-a-ponta pela lane barata |
| **F2 Context-pack** | pack.mjs+feature-md schema+TTL/freshness | pack real hashado; dry-run validando missão |
| **F3 Gates** | receipt runner+clausura fria+**spec micro dos 4 tipos de critério**+risk resolver+anti-loop | falso claim plantado pego pelo runner; dual-gate só em risco alto |
| **F4 Coordenador** | CAS/lease/fencing+sessão-por-feature+**PILOTO: missão real pequena** | 2 features paralelas integram sem quebra |
| **F5 Calibração** | telemetria→política (dados locais substituem chutes universais)+deck viewer+drill completo | números reais calibrando routing.json |

**Processo por fase (regra do operador — CONSTITUCIONAL):**
1. Conversa de micro-design seção por seção (como este spec foi feito), operador aprovando cada parte. Ex.: F1 terá conversa própria sobre "como funciona a skill de review, o que o cartão de feature diz linha a linha".
2. Pass GPT: Sol construtivo (o que falta?) + adversarial (onde quebra?), regra de 3 rodadas.
3. Aprovação do operador sobre o design convergido.
4. Implementação em INCREMENTOS CONVERSADOS com checkpoints — nunca "executei a fase inteira sozinho".
5. Prova da fase demonstrada no piloto antes de abrir a próxima.

**Migração 0.4→0.5:** estados LEGACY→MIGRATING→DUAL-READ→CUTOVER (+ROLLED-BACK). Trabalho em voo termina no 0.4 ou re-valida manifest no 0.5 — nunca meio-a-meio. Tabela artefato-0.4→evento-0.5 no design de F0. Backup do ledger antes do cutover.

**Non-goals (não construir):** daemon/serviço/DB · RAGflow/embeddings · sessão de milestone · deck com ações mutáveis · multi-hub/multi-máquina · OTEL collector · números universais sem telemetria local (fatia 1h, janela 40-60%, 10× KV).

## 8. Emendas — rodada Sol #1 (2026-07-29, passes construtivo + adversarial)

Filtro aplicado (diretriz do operador): aceitar o real com a solução MAIS SIMPLES que fecha o buraco; refutar over-engineering para 1 op/1 máquina.

**A1 (F0) Protocolo de escrita do ledger.** Hub e hooks são processos Node distintos → exclusão mútua obrigatória: lockfile único + append+fsync; evento com idempotency key; recuperação determinística trunca só tail não-validado pela cadeia de hash. KATs de emit/project concorrentes e escrita interrompida (Windows/NTFS).

**A2 (F0) Checkpoint atômico único.** Cursor embutido no state.json (com seq + hash do estado + hash do último evento); escrita temp+fsync+rename; validação antes de todo consumo; qualquer desvio → rebuild total do log. Elimina classe "dois arquivos dessincronizados".

**A3 (F0/F1) Reconcile-on-touch (sem daemon), com ordem obrigatória.** Nenhum observador dorme esperando deadline: todo comando `/harness` e todo hook PRIMEIRO reconciliam — em duas etapas de ordem fixa: **(1) drenar disco**: varrer `.mnfs/acks/` e `.mnfs/claims/` por artefatos ainda não materializados e emitir os eventos correspondentes; **(2) só então expirar pendências vencidas** (BOOT-ACK timeout, lease expirado, worktree órfão) com transições idempotentes (DISPATCHED→FAILED etc.). Anti-TOCTOU (corrida entre dreno e expiração): (a) FAILED-por-timeout só é emitido após revalidar o artefato do attempt no instante da decisão, dentro do lock do ledger (A1); (b) FAILED-por-timeout é REVERSÍVEL por regra determinística — dreno posterior encontra artefato durável do attempt → evento `LATE_ARRIVAL` compensa PARA O ESTADO QUE O ARTEFATO PROVA, respeitando a FSM: `.ack` tardio → FAILED→IMPLEMENTING (equivale a BOOT-ACK; segue aguardando CLAIM sob o mesmo deadline de implementação); `.claim` tardio validado → FAILED→IN-REVIEW. Nunca pula estado: só CLAIM durável validado avança a IN-REVIEW. Se já houve re-dispatch, `attempt_id` desambigua (artefato de attempt supersedido é registrado e ignorado). Chegou tarde ≠ perdeu. Promessa ajustada: timeout detectado no próximo toque, não no instante exato. KATs: mensagem perdida + Desktop fechado + claim em disco com hub morto + **interleaving: gravar ACK-only ou CLAIM entre revalidação e append do FAILED, com e sem re-dispatch → estado final IMPLEMENTING/IN-REVIEW/supersedido conforme regra, nunca FAILED terminal**.

**A4 (F0) Ledger é o outbox.** Evento DISPATCHED gravado ANTES de enviar mensagem; `dispatch_id` + `attempt_id` imutáveis em toda mensagem/evento/claim; resume idempotente (reconcile escaneia worktrees/refs/receipts antes de re-despachar).

**A5 (F1) Envelope MCP mínimo + disco como canal durável.** `{message_id, dispatch_id, attempt_id, sender, event_seq, payload_hash}`; dedup por message_id (at-least-once); resync = ler o ledger. Regra de durabilidade (1 máquina = disco compartilhado): worker grava `.mnfs/acks/<attempt>.ack` e `.mnfs/claims/<attempt>.json` ANTES de enviar a mensagem — mensagem é só notificação/despertador; o artefato em disco é o canal. MCP perder mensagem + worker morrer = estado ainda fecha, porque o reconcile (A3 etapa 1) drena o disco. SEM retry/backoff machinery.

**A6 (F0) Contrato operacional de hook.** Deadline por hook medido contra o limite real do Claude Code; caminho read-only cacheado; max-delta de projeção; exit codes determinísticos; fail-closed SÓ em transições protegidas nomeadas; evento break-glass do operador para destravar. Benchmark antes de ligar enforcement.

**A7 (F1) Lane barata com classificador conservador desde o dia 1.** Não espera o risk resolver de F3: allowlist explícita versionada de paths/efeitos inofensivos; desconhecido/alcance indisponível = gates máximos. Resolver completo de F3 substitui a allowlist.

**A8 (F3/F4) Worktree por attempt + fila de integração.** Worktree/index dedicados e nomeados por attempt; limpeza via `/harness gc` (comando, não serviço); integração sequencial no hub (fila natural de 1 operador) com recompute obrigatório do perdedor. KAT: 3 merges concorrentes + rebase em cascata + index.lock.

**A9 (F0) Cobertura de telemetria.** Campo `coverage: complete|partial` por attempt (compaction detectada, parse falho, janela incompleta → partial); attempt partial NUNCA calibra política em F5 — usa estimativa conservadora.

**REFUTADO — receipt assinado/MAC/capability contra worker malicioso.** Modelo de ameaça errado para 1 op/1 máquina: worker é sessão confusa, não adversário. Âncora de confiança já existe: merge-gate reexecuta a clausura fria ELE MESMO — receipt forjado/errado morre aí. Receipt = evidência intra-loop; decisão de merge = execução própria do gate. Registrado: se um dia multi-máquina/multi-usuário, revisitar.

## 9. Riscos aceitos e mitigações

- **Timeout de hook**: runtime deve ser rápido → projeção incremental com cursor; medir no F0.
- **Formato do transcript pode mudar**: parser versionado + degrade-to-unknown; nunca trava trabalho.
- **Custo da clausura fria não medido**: telemetria desde F0; ajuste em F5 com dado, não fé.
- **Cadeia de hash em jsonl é detecção, não prevenção**: suficiente para 1 op/1 máquina; ameaça é bug/truncamento, não adversário.
